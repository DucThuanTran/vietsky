# Incident 01 · Source API returns HTTP 500

**Drill date:** 2026-11-28 · `VIETSKY_CHAOS=api_500 run_pipeline.py --date 2026-11-28 --source weather` · run `b5882a56`
**Severity:** high (no new data for one source) · **Time to detect:** 16 seconds

## Symptoms
The weather `extract` stage FAILED. No new raw files were written, and staging and the mart were unchanged.

## Detection
- **stdout:** `Retry 1/4 after 2s: HTTP 500` → `2/4 after 4s` → `3/4 after 8s`.
- **`ops.pipeline_runs`:** `weather | extract | FAILED | 16s | https://api.open-meteo.com/v1/forecast failed after 4 attempts: HTTP 500`.
- **Airflow:** the `extract_weather` task turns red after 2 Airflow-level retries (1 minute apart).
- **Dashboard Operations page:** the latest run shows `FAILED`, and weather freshness keeps growing until it breaches the 24h SLA.

## Scope
The failure is at the **source** (extract). Downstream stages never ran (`continue` / upstream_failed), so no bad data went further.

## Root cause (5 Whys)
1. Why is there no new weather data? Extract FAILED.
2. Why did extract fail? All 4 API calls returned 500.
3. Why 500? The Open-Meteo server failed (simulated here by `chaos.http_status`).
4. Why didn't the pipeline recover on its own? The in-code retries only wait 14 seconds in total, and the outage lasted longer.
5. Why would nobody notice? Before Airflow there was no alerting. Now Airflow marks the task red and the dashboard shows it.

## Fix
Wait for the source to recover, then re-run the same date (the pipeline is idempotent): Clear the task in Airflow, or run `run_pipeline.py --date 2026-11-28 --source weather`.

## Prevention
- Keep two retry layers: in code (seconds, for blips) and in Airflow (minutes, for longer outages).
- Each run fetches an 8-day window, so a missed day is backfilled by the next day's run. Data is only lost if the source is down for more than 8 days.
- Alert (Slack/email) on task failure via Airflow's `on_failure_callback`.
